# 前端组件化审计报告

> 审计对象：`web/src`（38,939 行 TS/TSX，89 个文件）
> 审计视角：**组件化** —— 哪些该抽没抽、哪些抽了用不上、哪些是伪轮子
> 审计日期：2026-11-02
> 结论：**不是"没有组件化"，是"组件化停在了文件层级，没进到函数层级"**

---

## 一、先说清楚判断标准

组件化不是"把代码切小"，也不是"多写几个 `export function`"。
一个重复了三遍的东西该不该抽，看三条：

| 判据 | 说明 |
| --- | --- |
| **改一次要碰几个文件** | 改一个视觉细节要改 6 个文件 → 该抽。改一次只碰 1 处 → 不抽 |
| **语义是否同一个东西** | 两个 `.kpi` 长得一样但含义不同（指标 vs 表单摘要），抽了会互相绑架 |
| **抽出来之后调用点是否更短** | 抽完调用处从 5 行变 5 行、只是搬了个家 → 白抽 |

**这三条里，第三条最容易被忽略。** 很多"组件化改造"失败就失败在这：
文件行数少了，但读代码的人要在两个文件之间来回跳，总理解成本反而升高。

本报告只推**通过三条判据**的抽取。看着像重复但其实不该抽的，单列一节说明。

## 二、最核心的问题：组件化止步于文件边界

### 2.1 数据

| 文件 | 行数 | 情况 |
| --- | --- | --- |
| `views/Settings.tsx` | 2284 | 15 个组件，但 `LayoutSection`/`DiarySection`/`PomoSection` 等各自 200–400 行 |
| `views/Ledger.tsx` | 1726 | **`LedgerView` 一个函数占 1516 行**（76–1591 行） |
| `features/media.tsx` | 1793 | 混着工具函数、HTML 生成、组件、CSS 注入 |
| `modules/ModuleList.tsx` | 1255 | 6 个 Module 组件 + Shell + Dialog |
| `views/Notes.tsx` | 1079 | 单组件 |

### 2.2 `LedgerView` 是最典型的样本

```
76   export function LedgerView() {
       ... 37 个 useState
118  /* ---------- 账户管理 ---------- */
122  /* ---------- 预算 ---------- */
127  /* ---------- 周期账单 ---------- */
437  /* ---------- 账户 ---------- */      ← 状态 + 处理函数，约 95 行
532  /* ---------- 预算 ---------- */      ← 约 28 行
560  /* ---------- 周期账单 ---------- */  ← 约 60 行
756  <div className="card">                ← 收支总览
784  <div className="card lg-charts">      ← 九张图，195 行 JSX
979  <div className="card">                ← 筛选条
1090 <div className="card lg-filter">
1119 <div className="card lg-day">         ← 按天分组明细
1173 <div className="card">                ← 账户 + 预算 + 周期
1595 }                                     ← 函数结束
```

**这已经是六个页面塞在一个函数里了。** 代码作者自己也知道 ——
`/* ---------- 账户管理 ---------- */` 这类注释就是在划组件边界，
只是边界只活在注释里，没变成代码结构。

代价是具体的，不是审美问题：

- **37 个 useState 共处一个作用域**，任何一处 `setState` 都让整个 1520 行的
  JSX 重新求值。改预算输入框，九张图跟着重算。
- **函数内部有 45 处 `await`**，分布在 3 个业务区块的增删改里，
  每个都闭包捕获了整片状态。想复用"保存账户"的逻辑，只能连整个 `LedgerView` 一起搬。
- **`accountId` 一个状态被 4 个区块读**（记一笔、账户卡、筛选、周期账单）——
  它现在是"模块级变量"，不是"账户卡自己的状态"。

### 2.3 怎么拆（按依赖关系，不是按行数平均切）

`LedgerView` 里有三类东西，混在一起：

| 类别 | 例子 | 去处 |
| --- | --- | --- |
| **真·页面级状态** | `ym`（当前月份）、`data`（当月账目）、`insight`（图表数据） | 留在 `LedgerView` |
| **区块私有状态** | `accDraft`/`recId`/`rAmount`/`bTotal`… | 跟着区块走 |
| **跨区块共享** | `accounts`、`accountId`、`loadAccounts` | 上提到 `LedgerView`，用 props 下传 |

拆完的形状：

```
views/Ledger.tsx            ← 只剩：月份切换、数据加载、区块拼装（约 300 行）
views/ledger/AccountCard.tsx    ← 账户卡（含拖拽排序、行内编辑）
views/ledger/BudgetCard.tsx     ← 预算卡
views/ledger/RecurCard.tsx      ← 周期账单
views/ledger/EntryForm.tsx      ← 记一笔
views/ledger/DayList.tsx        ← 按天分组明细
views/ledger/ChartsCard.tsx     ← 九张图（现在已部分在 LedgerCharts.tsx）
```

**关键约束：拆的时候不许改 DOM 结构。**
100 个 CDP 探针里大量靠 `className`/`data-*` 定位，
结构调整会让探针误报，进而分不清是"改坏了"还是"探针过时"。

## 三、四个够格抽出来的轮子

### 轮子 1 · `useConfirm` —— 33 处原生 `window.confirm`

**现状**

```tsx
// 33 处，写法有 3 种变体
if (!window.confirm('删除画板「x」？')) return;
if (!confirm('删除这条？')) return;              // 少了 window.
const ok = window.confirm(msg); if (!ok) return; // 另一处又换个写法
```

**为什么这是真问题（不只是风格）**

原生 `confirm` 在本项目里是**破坏一致性最严重**的一处，因为：

1. **它和产品调性完全冲突。** 这个产品的对话框是 `--panel` 底、圆角、
   自绘 ✕ 按钮；`confirm` 是 Windows 系统灰框。用户点了"删除"，
   弹出的是浏览器风格的框，会有"这不是同一个软件"的错位感。
2. **它阻塞主线程。** `confirm` 期间页面完全静止，WebView2 里的动画全停。
3. **它没法表达"危险等级"。** 33 处里 7 处是**不可逆**的
   （"删了就找不回来了"），26 处是可恢复的。原生框长得一模一样，
   用户无法从视觉上区分"点错就完了"和"点错还能撤回"。
4. **它不认主题。** 深色主题下弹出浅色系统框。

**该抽成什么**

```tsx
// components/Confirm.tsx —— 复用 ui.tsx 已有的 Dialog，而不是新造
export interface ConfirmOpts {
  title: string;
  body?: ReactNode;
  /** danger = 不可逆（红按钮 + 二次确认文案）；normal = 可恢复 */
  tone?: 'danger' | 'normal';
  okText?: string;
  cancelText?: string;
}
export const confirmDialog = (o: ConfirmOpts) => useConfirm.getState().ask(o);
```

形态照抄现有的 `askText`（`ui.tsx:188`），它已经是 Promise 化 + zustand 托管，
证明这个模式在本项目跑得通。**不要发明新机制，复制已成功的那个。**

**注意：不能一次全换。** 33 处里有的在 `useEffect` 回调里、有的在 `map` 里，
替换后都要变 `async`。建议分批，从 `views/` 开始，`features/` 后跟。

### 轮子 2 · `EmptyState` —— 104 处，且语义被混用

**现状**

```tsx
<div className="empty">还没有数据。</div>
<div className="empty small">还没有数据。</div>
<div className="empty" style={{ gridColumn: '1/-1' }}>还没有图片</div>
<div className="empty" style={{ padding: '24px 0', textAlign: 'center', opacity: 0.7 }}>
```

104 处调用里，至少 **8 处各自内联覆盖** `padding`/`textAlign`/`opacity`/`gridColumn` ——
说明 `.empty` 这一个类名承担不了这么多场景。

**更严重的是语义混淆：**

```tsx
{busy ? <div className="empty">读取中…</div> : ...}   // 加载中
{err  ? <div className="empty">没读到：{err}</div> : ...} // 出错
{!n   ? <div className="empty">还没有数据。</div> : ...} // 真空
```

**三种完全不同的状态，用同一个视觉。** 后果是：慢机器上用户看到
"还没有数据"字样，分不清是"真的没有"还是"还没读完"，
于是刷新页面 —— 而刷新会让加载重新开始。这是一个**自我强化的坏体验**。

**CSS 还叠了一层坑：** `.empty` 在 `styles.css` 里定义了两次
（884 行 `padding:10px 2px` / 2819 行 `border:1px dashed`），
后者覆盖前者，于是 104 处按"一行淡字"写的调用，现在渲染成带虚线框的大盒子。

**该抽成什么**

```tsx
export function EmptyState({ kind = 'empty', text, note, action, icon }: {
  kind?: 'empty' | 'loading' | 'error';
  text: ReactNode;
  note?: ReactNode;
  action?: ReactNode;       // 「新建画板」这类按钮，现在散在各处的 .empty 里
  icon?: IconName;
}) 
```

三态各自有明确的视觉：`empty` 虚线框 + 图标、`loading` 骨架/转圈、`error` 红色提示 + 重试按钮。

### 轮子 3 · `StatCard` —— 40 处 `.kpi` 手写

**现状**：`.kpi > .k / .v / .s` 三层结构，在 6 个文件里手写约 40 遍。

```tsx
// Stats.tsx:204
<div className="kpi">
  <div className="k"><Icon name="sparkle" size={12} />当前连续</div>
  <div className="v">{s.streak}<small>天</small></div>
  <div className="s">最长 {s.longestStreak} 天</div>
</div>

// Ledger.tsx:758 —— 同样三层，只是多了 color
<div className="kpi">
  <div className="k">收入合计</div>
  <div className="v" style={{ color: 'var(--ok)' }}>{amt(data?.income || 0)}</div>
  <div className="s">进账 {inN} 笔</div>
</div>
```

**为什么该抽**：符合判据 1 —— 想给所有指标卡加"点击下钻"或"数字滚动动画"，
现在要改 6 个文件 40 处。抽完改 1 处。

**为什么排第三**：符合判据 3 —— 抽成组件后调用点不会短多少
（`<StatCard k="收入合计" v={amt(x)} s="进账 3 笔" />` 也就省 2 行）。
它的收益在**未来**（统一交互），不在当下。

```tsx
export function StatCard({ label, value, unit, sub, icon, tone, onClick }: ...)
export function StatGrid({ children, cols }: ...)
```

### 轮子 4 · `useSetting` —— 146 处 `setSetting` + 52 处 `=== '1'`

**现状**：设置的存储格式是**字符串**，于是每个布尔开关都要手工编解码。

```tsx
// 52 处这个
<Switch
  on={String(settings.navCollapsed) === '1'}
  onClick={() => void setSetting('navCollapsed', String(settings.navCollapsed) === '1' ? '0' : '1')}
/>
```

`String(...)` + `=== '1'` + 三元 `'0'/'1'`，一个开关三处重复。
`Switch` 组件本身只接 `boolean`，转换的活儿全推给了调用点。

**该抽成什么**

```tsx
export function useBoolSetting(key: string, def = false) {
  const v = useStore((s) => s.settings[key]);
  const set = useStore((s) => s.setSetting);
  return [String(v) === '1', (next: boolean) => void set(key, next ? '1' : '0')] as const;
}
// 调用点
const [collapsed, setCollapsed] = useBoolSetting('navCollapsed');
<Switch on={collapsed} onClick={() => setCollapsed(!collapsed)} />
```

同类还有 `useNumSetting` / `useStrSetting`。**这里已经有一个真实的显示不一致**：

```tsx
// CacheCenter.tsx:180-182 —— 显示的、和真正传给后端的，用了两套默认值
<b>{Number(settings.cacheDays) || 30} 天</b>                          // 界面显示 30
await api.cache.prune(Number(settings.cacheDays) || 0, ...)          // 实际传 0
```

同一个设置项，界面告诉用户"保留 30 天"，清理时却按 `0` 传下去。
`||` 把合法的 `0` 当成了"没设置"。这类地方统一走 `useNumSetting(key, def)`
之后，默认值只有一处定义，就不会再分叉。

**为什么排第四**：`setSetting` 的 146 处里有 83 处在 `Settings.tsx` 一个文件，
局部看并不散。抽是给未来省事，收益不如前三个立刻。

## 四、看着像重复、但**不该抽**的（排除清单）

这一类同样重要 —— 抽错了比不抽更糟。

| 现象 | 次数 | 为什么不抽 |
| --- | --- | --- |
| `className="inp"` | 196 | 构成是 `<input>` 145 / `<select>` 34 / `<textarea>` 16。**input 不该抽**：全是裸标签加个类，没有结构，抽成 `<Input>` 只会让调用点变长，还得透传 `type`/`value`/`onChange`/`ref` —— 而 `React.InputHTMLAttributes` 透传本身就是框架现有能力，包一层是倒退。**`<select>` 那 34 处值得单独看**：它们都是「一个值 + 一组固定选项」，`children` 是 option 列表，这才是真有结构的重复（见下） |
| `api.xxx()` 后的 `try/catch + toast` | 102 | 看着该抽成 `useAsync`。但实测：**178 种不同提示文案，只有 27 种重复**（最多的是「已保存」10 次、「已移到回收站」「已删除」各 7 次）。文案是贴着具体场景写的（"没存上，再试一次" / "账目没读出来，稍后再试" / "顺序已保存"），抽成统一包装等于把 178 条具体信息压成 1 条泛泛的"操作失败"。**这里的重复是表象，差异才是本体** |
| `find → map → filter` 的列表渲染 | 大量 | 这是 JS 不是 UI。`.map` 就是最合适的抽象，再包一层 `List` 只会让 key / 空态 / 分片的处理更绕 |
| 各自的 `useEffect` 加载 | 38 | 触发条件（依赖数组）几乎每个都不同。合并成 `useLoad(fn, deps)` 只是把 `useEffect` 改个名字 |
| `Ledger.tsx` 里 `money()`/`amt()` | 2 处 | 只有两处用，抽成全局工具函数反而扩大暴露面。**保持局部** |
| 各页面的 `Topbar` | 已抽 | `ui.tsx:44` 已有，做得对 |

**一条元规则**：判断"该不该抽"时，先问"抽出来之后，
调用点是在**描述意图**还是在**转达参数**"。
`<StatCard label="收入" value="¥100" />` 是在描述意图 —— 好。
`<Input className="inp" {...rest} />` 只是转达参数 —— 白抽。

### 补充：那 34 处 `<select className="inp">` 是另一回事

它们和裸 input 不同 —— 每个都带一组选项，结构是「一个值 + 一组固定选项」：

```tsx
<select className="inp" value={listId} onChange={(e) => setListId(e.target.value)}>
  {lists.map((l) => <option key={l.id} value={l.id}>{l.name}</option>)}
</select>
```

**这和 `SetRow.tsx` 里已有的 `Chips` 是同一语义**（`value` + `items` + `onPick`），
只是一个渲染成按钮组、一个渲染成下拉。所以正确的动作不是新建 `Select` 组件，
而是**把 `Chips` 的语义提炼成一层 `Choice`，两种外观共用一套 props**：

```tsx
type ChoiceProps<T extends string> = {
  value: T;
  items: [T, string][];
  onPick: (v: T) => void;
  look?: 'chip' | 'select';   // 同一份数据，两种外观
};
```

但这属于**收益中等、优先级靠后**的动作 —— 34 处也不算多，
而且现在两种写法各自都能正常工作。列在这里是为了避免
下次有人看到"34 处 select"就直接去造一个 `<Select>` 组件（那会变成第三个轮子）。

## 五、CSS 侧：172 个类名重复定义

```
类名总数 748，重复定义 172 个
on        41 次   ← 选中态，每个组件各定义一遍自己的 .xxx.on
inp       12 次
card       8 次
nav        7 次
chip       7 次
```

`.on` 41 次不算错（`.chip.on` 和 `.nav.on` 本来就该不同），
但要确认没有**互相打架**的：`.empty` 那个就是真打架（后定义覆盖前定义，
导致 104 处调用的视觉和预期不符）。

**建议动作（低成本）**：
1. 先修 `.empty` 的双重定义 —— 合并成一处，明确它是"带虚线框的块"
2. 加一条约束写进 `styles.css` 头部注释：**同类不许在文件后段重新定义，
   要改回去改原处**。否则 3611 行的 CSS 会继续长出更多"后覆盖前"

## 六、优先级与风险评估

| 顺序 | 动作 | 改动面 | 收益 | 风险 |
| --- | --- | --- | --- | --- |
| 1 | 拆 `LedgerView` → 6 个子组件 | 大（1 文件 → 7 文件） | 极高：解除 37 状态耦联 | 中：必须保持 DOM 不变 |
| 2 | `EmptyState`（含三态 + 修 `.empty` 双定义） | 中（104 处调用，但机械） | 高：修掉"加载/空/错"混淆 | 低 |
| 3 | `useConfirm` + 自绘确认框 | 中（33 处，需改 async） | 高：一致性与危险分级 | 低 |
| 4 | `StatCard` / `StatGrid` | 中（40 处） | 中：为将来交互铺路 | 低 |
| 5 | `useBoolSetting` 等 | 小 | 中 | 低 |
| 6 | 拆 `SettingsView` 2284 行 | 大 | 高 | 中 |

**为什么 `LedgerView` 排最前，尽管它风险最高**

因为它是**所有问题的放大器**。37 个状态在一个作用域里，
意味着任何想复用账户逻辑的尝试都得先面对这一坨。
先拆它，后面四个轮子才有地方装 —— `AccountCard` 抽出后，
`EmptyState` 在账户空列表处立刻有用武之地。

反过来，先抽 `EmptyState` 再拆 `LedgerView`，等于拆的时候
还要顺带处理刚改过的 104 处，两件事纠缠。

**测试保障**：`tests/` 下 100 个 CDP 探针是这次重构的底气。
重构期间每拆一个区块，就跑 `verify-pages.js`（23 页渲染）
+ `verify-all-readonly.js`（103 个只读接口）。
**不允许在探针基线变红的情况下继续往下拆。**

## 八、状态

**本报告只做审计，未改任何代码。**

建议的落地方式是**分步、可回退**：

1. 先做 `EmptyState` + `.empty` 修复（收益立刻可见、风险最低），跑一轮探针建立信心
2. 再做 `useConfirm`（独立于页面结构，不动 DOM）
3. 然后集中攻 `LedgerView` 拆分（一次性做完，不半途停下）
4. `StatCard` / `useSetting` 最后收尾

每一步都要：`npm run build` → `dotnet build -c Debug` → 跑探针 →
更新 `changelog.ts` + 开发文档。**不发布。**
