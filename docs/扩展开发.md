# 扩展开发

给「日签」做主题、插件、内容包。三种东西共用一个文件格式，靠 `kind` 区分。
不需要编译、不需要写代码 —— 一个 JSON 文件就是一份扩展。

---

## 1. 包的基本样子

所有包都是一个 JSON 对象，公共字段先行：

```json
{
  "rq": 1,
  "kind": "theme",
  "id": "yourname.warm-paper",
  "name": "暖阳纸",
  "version": "1.0.0",
  "author": "你的昵称",
  "desc": "一句话说明",
  "home": "https://example.com/your-pack"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `rq` | ✅ | 格式版本，当前是 `1`。程序遇到不认识的版本会拒绝，不会瞎猜 |
| `kind` | ✅ | `theme` / `plugin` / `workshop` |
| `id` | ✅ | 唯一标识，只允许字母数字 `.` `_` `-`。建议用 `作者.包名` 的形式，避免和别人撞 |
| `name` | ✅ | 显示给人看的名字 |
| `version` | ✅ | 版本号，`1.2.3` 这种点分数字。同名包重复安装时靠它判断是升级还是降级 |
| `author` | | 作者 |
| `desc` | | 一句话说明，装之前的预览里会显示 |
| `home` | | 主页 / 仓库地址 |

`id` 一旦发出去就**不要再改** —— 用户已经装的记录、导出的包、卸载逻辑全靠它认人。

## 2. 主题包（`kind: "theme"`）

```json
{
  "rq": 1,
  "kind": "theme",
  "id": "yourname.warm-paper",
  "name": "暖阳纸",
  "version": "1.0.0",
  "base": "paper",
  "colors": {
    "bg": "#fdf6e8",
    "panel": "#fffaf0",
    "ink": "#3b3228",
    "accent": "#c9793a"
  }
}
```

- `base`：底色从哪套内置主题继承。可选 `paper` / `ink` / `night` / `forest` / `rose` / `mono` / `semi`。
  不填就用安装时用户当前的主题。
- `colors`：可以只给几个槽，**没给的从 `base` 继承**。不必凑满 16 个。

### 可用的 16 个色槽

| 组 | 槽 | 含义 |
|---|---|---|
| 背景 | `bg` | 页面底色 |
| | `side` | 侧边栏 |
| | `panel` | 卡片 / 面板 |
| | `panel2` | 次级面板 |
| 文字 | `ink` | 正文 |
| | `ink2` | 次要文字 |
| | `ink3` | 弱化文字 |
| 线条 | `line` | 分隔线 |
| | `line2` | 浅分隔线 |
| 强调 | `accent` | 主色 |
| | `accent2` | 主色（深） |
| | `accentSoft` | 主色浅底 |
| 语义 | `ok` | 成功 |
| | `warn` | 警告 |
| | `bad` | 危险 |
| | `blue` | 链接 / 信息 |

### 颜色写法是硬约束

只接受 `#rgb` 或 `#rrggbb`。**别的写法一律拒绝**。

原因很直接：这些值会被写进 CSS 变量。如果允许 `red; background-image: url(...)` 这种，
一个主题包就等于拿到了任意样式注入的能力。所以这里只认六位十六进制。

### 怎么做一套

不想手写 hex，用程序里现成的：

1. 设置 →「外观」→ 调一套自己满意的配色
2. 主题 →「做一个」→ 填名字和 id → 生成
3. 导出的 JSON 里 `colors` 是**算好的 16 个值**（不是差量），别人装上去就是你现在看到的样子

## 3. 插件包（`kind: "plugin"`）

插件往用户的日记里**加东西**。它不执行任何代码 —— 能被 JSON 描述的东西才装得安全。

```json
{
  "rq": 1,
  "kind": "plugin",
  "id": "yourname.three-good-things",
  "name": "今日三件好事",
  "version": "1.0.0",
  "modules": [
    { "type": "heading", "title": "今天的三件好事" },
    { "type": "richtext", "title": "第一件" },
    { "type": "richtext", "title": "第二件" },
    { "type": "richtext", "title": "第三件" }
  ],
  "tags": ["感恩"],
  "todoLists": ["睡前清单"],
  "settings": {
    "plugin.threeGood.remindAt": "22:00"
  }
}
```

### `modules` —— 能加哪些模块

只能用日记里已经存在的类型：

`richtext` `mood` `weather` `tags` `habits` `todo` `sleep` `energy` `rating` `images` `quote` `heading` `divider`

每项可以带 `config`（对象），会写进模块配置。**别在 config 里塞用户私人内容** ——
用户导出插件时，config 会跟着走。

### `settings` —— 只能写 `plugin.` 开头的键

这是**硬性限制**，不是建议。

一个插件如果能写 `theme`、`dataRoot`、`passwordHash`，那它就不是扩展，是接管。
所以所有设置键必须以 `plugin.` 开头，否则整个包会被拒绝。

### `tags` 和 `todoLists` 的现实约束

- **标签**在库里没有独立的表 —— 它是从各天日记的标签聚合出来的。
  所以插件安装标签时，只能挂到用户**已经写过**的日记上。
  全新空库时会跳过并告诉用户跳过了几个，**不会为了建标签凭空造一篇日记**。
- **待办清单**是有独立表的，能正常新增。

### 重装 / 升级的代价

同名包重装时，程序会先把上一版拆掉再加新的（而不是增量叠加）——
否则改了模块标题、删了一个模块，会留下一堆孤儿模块，用户删都不知道从哪删。

代价是**用户对上一版模块做的自定义会丢**。这个代价在 UI 上会明确警告，不会默默吃掉。

## 4. 内容包（`kind: "workshop"`）

```json
{
  "rq": 1,
  "kind": "workshop",
  "id": "yourname.daily-template",
  "name": "读书笔记模板",
  "version": "1.0.0",
  "work": "templates",
  "items": [
    { "name": "读书笔记", "body": "## 书名\n\n## 一句话总结\n\n## 三个收获\n1. \n2. \n3. \n\n## 想做的事\n" }
  ]
}
```

`work` 有四种：

| work | items 每项的形状 | 说明 |
|---|---|---|
| `templates` | `{ name, body }` | 日记模板。只新增，不覆盖已有的 |
| `countdowns` | `{ title, date, repeat?, color?, note? }` | 倒计时。`repeat` 支持 `yearly` / `monthly` / `lunar-yearly` / `lunar-monthly` |
| `tags` | `{ name }` | 标签体系。同样受"必须先有日记"的约束 |
| `ledgerCats` | `{ name }` | **只能导出，不能导入** |

### 为什么 `ledgerCats` 不能导入

记账分类在库里不是一张表，它是记账记录上的字符串，前端从历史记录里聚合出可选列表。
也就是说：**没有记账记录就没有分类**。

与其伪造一条 0 元记录来撑起分类，不如直接说这个类型暂不支持导入。伪造数据比功能缺失更糟。

## 5. 装完之后发生了什么

程序把这些记在 `settings.extRegistry` 里（一份 JSON 清单）：

```json
{
  "v": 1,
  "items": [
    {
      "kind": "plugin",
      "id": "yourname.three-good-things",
      "name": "今日三件好事",
      "version": "1.0.0",
      "at": "2026-11-01 21:40",
      "enabled": true,
      "raw": "{ ...包原文... }",
      "moduleIds": ["m_xxx", "m_yyy"],
      "createdTags": ["感恩"],
      "createdLists": ["l_zzz"],
      "settingKeys": ["plugin.threeGood.remindAt"]
    }
  ]
}
```

**保留 `raw` 是有意的**：卸载之后想重装、或者想把这个包再发给别人，
都靠原文还原，不靠"从当前状态倒推"。倒推出来的东西和原包不会一样。

### 卸载按 id 精确删

- 模块：按 `moduleIds` 里的 id 删
- 清单：按 `createdLists` 里的 id 删
- 标签：按 `createdTags` 里的名字从各天日记上摘掉
- 设置：按 `settingKeys` 里的键清掉

所以**你后来自己改过标题的模块、自己新建的同名标签，不会被误删**。

## 6. 主题包的槽位机制

装来的主题不在内置主题表里（那是编译进代码的常量，运行时加不进去），
而是占 `themeCustom['pack:<id>']` 这个槽。

这样带来三个好处：

1. 不会和内置的 `paper` / `ink` / `night` 撞名
2. 卸载时一眼能看出哪些槽是装来的
3. 同一个包重装 / 升级，覆盖的是自己那一个槽，不会越装越多

同一时刻只有一套主题生效。装一个新主题包会自动把其它已启用的主题包标成停用；
切回内置主题时，装来的那些也全部停用。

## 7. 调试你的包

程序里没有扩展开发控制台，但包是纯 JSON，校验逻辑都写得很直白：

1. 把包拖进安装框 —— **会先给你看预览**，不会直接装
2. 预览里能看到解析出来的名字、版本、作者、摘要，以及会改动什么
3. 解析失败会给具体原因（不是合法的 JSON / 缺字段 / 颜色写法不对 / 模块类型不存在 / 设置键没加前缀）
4. 装错了点「卸载」就能干净退回

常见的失败原因：

- 用了中文引号 `“…”`，或者从聊天软件复制时被转义过
- 复制时丢了结尾的 `}`
- `kind` 和你要用的中心对不上（主题包装进了插件中心）
- 颜色写了 `red` 或 `rgb(255,0,0)` —— 只收 `#rrggbb`
- `settings` 里有键没加 `plugin.` 前缀

## 8. 分发方式

没有在线市场。程序是离线的本地日记本，没有服务端就没有可信的来源列表 ——
与其做一个假市场，不如把"装一个包"这件事做稳：

- 把 `.json` 发给别人（邮件、网盘、聊天软件都行）
- 对方在对应中心点「安装」，拖进去或粘贴
- 也可以用 GitHub 之类的仓库托管一堆包，让别人自己下载

**不要**在包里放可执行文件或脚本 —— 程序根本不认，也没有执行它们的能力。
